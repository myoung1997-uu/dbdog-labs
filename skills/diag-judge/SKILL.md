# 诊断判题

## 任务与材料

只评价当前这条 trace：预期根因找到了哪些，结论是否有证据支持，本次有哪些问题。
不读取历史判题、修复标记或未关闭问题，不跨轮去重、复验或关单。定期汇总由外部流程负责。
不修改执行 agent、调度机制、代码、skill、用例或现场，也不提出修复方案。

交付 `annotations.jsonl` 和 `summary.md`。先读 [输出契约](references/output.md)。
格式说明中的占位符是模板，不是已经核实过的案例。

包内先读 `cases/<event_id>/forward.md` 和 `ground-truth.md`，核查具体证据时读取 `trace.json`。
`reverse.md` / `probe.json` 如有可作补充，但其中的判断也要核实；没有不自动降级。
直接判 trace 时，用 `get_llmobs_trace` 获取本条轨迹，以 root 的 `dataset_record_id` 用
`get_llmobs_dataset_records` 获取题面和答案纸。需要可回流的包时由 `judge-run` / 导包脚本准备，判题不自行写服务端。

确认对象、诊断时间窗、agent 实际看到的题面和最终结论、答案纸来源。
判断指引或能力问题时，按需核对 agent 当时可用的工具、权限、skill 和适用的产品约定。
材料不足只限制依赖它的判断，记录缺什么、影响哪项判断；其余继续评价。

## 1. 判断根因命中

从最终结论提取 agent **实际认定**的根因。候选、已排除的假设不算命中。
按答案纸根因顺序逐条说明是否命中及理由：致因机制一致才算，允许不同措辞与合理路径；
只描述症状、列出可能性不算找到根因。结论猜中了仍可算命中，是否有依据在下一步单独评价。

预期根因全部命中不代表所有结论都正确。agent 额外提出的根因逐条记在 `roots.extra`，
说明有证据支持、与证据矛盾还是无法判断，以及具体依据。答案纸没写到不直接等于错误。
答案纸与事实冲突时明确提出争议，不自行改答案；无法据此划分根因时记录评价限制。

无答案纸或材料不足以评价根因，用 `unknown`。只有证据证明**诊断窗口内**故障没有出现，
才用 `not_reproduced`；现在查不到不能证明当时没出现。现场不成立也不掩盖本次已观察到的独立问题。

## 2. 检查结论的证据

针对最终结论的重要主张检查：
- 是否指到真实返回或可核实事实，数据的对象、时间窗、口径是否对应；
- 数据是否支持所说的原因，而不仅是描述了相关现象；
- 是否存在没有解释的反证，是否把“可能如此”写成“已经确认”。

有充分支持且无未解释的关键冲突为 `solid`；发现关键支持缺失、误读或断言过强为 `weak`。
材料缺失到无法检查时为 `unknown`，不要把判官缺材料当作 agent 没有证据。
已能确定关键证据有问题时，即使另有材料缺失也记 `weak`，并列明限制。
在 `findings.rationale` 说明各根因命中和重要主张的证据依据，带具体 span 或返回值。

只用 agent **当时已获得**的材料评价它的证据充分性。判官补查可以证明根因真实，
不能替 agent 补成绩。不要要求唯一诊断路径，也不要用“抽掉关键证据后结论不成立”判弱。

## 3. 识别并核实本次问题

从具体偏差出发：发生了什么、在哪一步、为何是问题、对本次诊断有什么影响。
不以是否知道修复方案决定是否记录。调用多或没有调用某个工具本身不构成问题，要说明具体无效行为或遗漏。

两个标签轴各回答一件事：

| 字段 | 取值与边界 |
|---|---|
| `issue_type` | `tool`：工具行为、返回或能力问题；`skill`：能指到具体指引错误、矛盾或缺失；`case`：题面或答案纸问题。描述问题类型，不猜修复仓库。 |
| `class` | `true_bug`：已证明工具或相关数据链路违反适用的预期行为；`needs_decision`：还需核实是否为缺陷，或已知缺口需人决定如何处理。 |

`needs_decision` 继续标明 `decision`：`wording` 指引问题、`capability` 能力缺口、
`case` 题目问题、`is_bug` 尚不能确认是否为缺陷。写清具体要核实或决定什么，不替人拟修复方案。

工具正常、指引清楚，agent 仍误读证据、提前收口或忽略结果：记录到 `observations`，
说明事实和影响，并反映到根因、证据评价。不要编造 skill 缺陷，不生成修改 agent 的任务，不增加 orchestration 分类。

必要时只读核实：先明确要区分的解释，选择有效的检查；证据足够就停止，无法继续就说明原因。
不机械走遍直查、对照、重放三条路，不重新制造故障或修改现场。
记录操作、结果、对象和时间窗；当前现场已变的，不直接拿当前结果否定本条 trace 的事实。

确认 `true_bug` 要说明：预期行为的依据、适用条件下的实际违背，以及为何不是正常空值、
合法报错或条件差异。重复报错只证明可重复，另一台实例有数据也不单独证明本台有缺陷。
数据缺失类问题需要证明同一对象、相关窗口内数据本该能拿到；其他错误按相应行为约定核实。

## 4. 写出结果

同一问题在当前 trace 的多处表现合并为一条，key 按现象命名，不读取历史来匹配。
每条问题说明事实、依据和影响。确认缺陷的 `repro` 用文字写清条件、操作和实际表现，
`expected` 写预期表现及依据；不要求复现脚本、额外证据文件包或修复方案。
指向当前 trace 的具体 span；补查的指针同时说明调用和结果，不能只写“已在线核实”。

`summary.md` 是本次结果的简短摘要：根因命中、额外结论、证据、主要问题和评价限制。
关键理由、agent 行为偏差和限制必须进入结构化结果，不能只留在摘要中。
历史比较、修复状态和关单不属于本次输出。
