# fix-run —— 修一道题挖出的问题

诊断飞轮的第四棒。`judge-run` 判完一条 trace，问题挂在那一次判题里；你这一棒把它们修掉。

怎么才算关：
- **确定是 bug 的**，你修完、部署、在原窗口复测通过，就关了，不等重跑。之后哪次判题又撞上它，自动重新打开。
- **其余的**（要人定的、数据修不回来的），关不关看之后判题的复验，不由你说了算。

复验只认修复之后跑出来的诊断：修复之前跑出来的诊断，今天重判几次看到的都是旧路径，撞上了也不作数。

**工作单位是用例**：一次修一道题挖出的全部问题，不是一次修一条。

**修完不触发任何东西**：要不要再跑、从哪一步跑，由人在页面上定。你只告诉他建议点哪一个按钮、为什么。

## 口令

- `fix-run <用例集>/<record id 前 8 位>`：修这道题。
- `fix-run`（不带参数）：领「判过、有没关的问题、且没人接」的用例里最新判过的那道。
- `/loop /fix-run`：自定节奏反复领。每一 tick 一道题；要人定的摆出来等回答，下一 tick 接着。

在**交互会话**里跑——要人定的必须讨论，headless 起不了。不需要租约：一个人跑、一次一道题，`claimed_fixed` 标记就是「有人接了」。

## 开跑前确认

| 要什么 | 是什么 |
|---|---|
| `DBDOG_BASE_URL` | dbdog server 的 API 面（不是 MCP 口） |
| `DBDOG_API_KEY` | 控制台签发的 key；已配 `DBDOG_OBS_API_KEY` 就复用那个值 |
| `DBDOG_OPERATOR` | 你是谁（如 `qinqiang`），落进修复标记的 `by`。没有就问用户，别编 |
| MCP | 会话挂着 dbdog 的 MCP：重放 `repro`、复测都要用 |
| 五仓兄弟检出 | `../dbdog-server`、`../dbdog-mcp`、`../dbdog-agent*`、`../dbdog-web`、`../dbdog-labs` 平级 checkout——判题不给落点，定位靠你在这里 grep |

脚本目录记作 `$S`：`S=$(claude plugin path dbdog-agent-obs 2>/dev/null || echo ~/.claude/plugins/dbdog-agent-obs)/skills/diag-flywheel/scripts`。

## 一道题怎么修

### 1. 拉材料

```sh
node $S/llmobs/loop-pending.mjs --dataset <用例集> --kind fix --json     # 不带参数时先看有哪些题等着修
node $S/llmobs/fix-context.mjs --record <record id> [--out fix-work]     # 导出这道题的修复工作包
```

工作包 `fix-work/<用例集>-<record 前 8 位>/`：

| 文件 | 是什么 |
|---|---|
| `README.md` | 题面、引擎、答案纸、最新判过那次的 trace / 结论 / 证据，**判题对整个诊断过程的分析**（走了什么路、从哪步开始偏） |
| `true-bugs.md` | 确定是 bug 的，逐条：怎么核出来的、怎么重放、修好后该看到什么、指针、已有标记 |
| `needs-decision.md` | 要人定的，逐条：定的是哪一种、请定什么、全部上下文、指针、已有标记 |
| `items.json` | 机器读的同一份，含每条的开关状态、挖出它的 trace、已有修复标记 |
| `spans/<span 前 8 位>.md` | 每个指针指到的那次调用：工具名、入参、返回前 2000 字 |

**先读 `README.md` 的过程分析，再读条目。** 知道 agent 是怎么走到那一步的，才知道一条问题在整个诊断里有多要紧。

同一条诊断可能判过好几次，工作包里每一次都算。已经有标记的条目看清是谁打的、打了什么，别重复修。

### 2. 确定是 bug 的，逐条

1. **先重放**：照 `repro` 那条调用在 MCP 上跑一遍。还错 → 往下走；**不复现** → 不改代码，打标记：
   ```sh
   node $S/llmobs/fix-mark.mjs --trace <trace_id> --key <key> --status needs_human --note "重放没复现：<你看到什么>" --by $DBDOG_OPERATOR
   ```
2. **定位**：拿 `how_verified` 里的工具名、字段名、错误串在五仓里 grep。判题方故意不给落点——它手上没有源码；你有。
3. **改**：改代码或配置。风格照各仓 git log；schema 改动只走各仓自己的迁移。
4. **测试**：跑该仓的测试。
5. **提交**：一条问题一个提交，提交信息带 `key`。
6. **部署**：改了哪个仓就「部署」哪个仓（家族军规 9：到 `../dbdog-build` 仓执行 `publish` skill 的快升级）。没部署，线上还是旧的，下面几步验的都是旧代码。同一个仓的几条可以改完一起部署一次。
7. **判断数据**：bug 修了，挖出它的那个窗口里的历史数据还是当时写进去的样子。直查底层存储（时序在 ClickHouse，控制面在 PG），看那段数据对不对，三选一：
   - `unaffected`：数据本来就对。纯读取或查询的错，库里没写坏东西。
   - `repaired`：数据错了，但能按确定的规则改回来，那就改回来。时序数据直接原地 UPDATE，不做备份。例：host 按来源 IP 猜错的那条，按 agent 写在数据包里的 host 把历史点原地改回来。
   - `unrepairable`：改不回来。比如当时就没采到，或者对的值已经找不回来。
   规则拿不准、要猜的，不算「能改回来」，记 `unrepairable`，别编数据。
8. **原窗口复测**：数据不是 `unrepairable` 的，在**挖出它的那次诊断的窗口**上原样重放 `repro`，看是不是变成了 `expected` 说的样子。窗口直接读工作包：`README.md` 的「复测窗口」一节，或 `true-bugs.md` 里这条的「挖出它的那次诊断的窗口」那一行（`items.json` 的 `window`）。
   写着「现场已过期，没法在原窗口复测」的，不带 `--verify`，`--note` 里照实写，收尾建议人点「复现」。
   `unrepairable` 的不复测——原窗口里的数据是错的，重放通过或没过，验的都不是这次修复。
9. **打标记**：`--note` 写你改了什么、重放拿到了什么（原样贴关键结果，别只写「通过」）。
   ```sh
   node $S/llmobs/fix-mark.mjs --trace <trace_id> --key <key> --status claimed_fixed \
     --data unaffected|repaired|unrepairable [--verify passed|failed] \
     --note "改了什么；原窗口重放拿到什么" --by $DBDOG_OPERATOR
   ```
   - 复测通过：`--verify passed`，这条就关了。
   - 复测没过：`--verify failed`，这条还开着。回第 2 步接着查；查不下去就照实打上，告诉用户。
   - 数据修不回来：只带 `--data unrepairable`，不带 `--verify`，页面上显示「数据修不回来，等下次诊断和判题时验证」。

`<trace_id>` 用挖出这条问题的 trace（`items.json` 里这条的 `trace_id`）。

判题给的判定链要是站不住（你重放发现它核错了），不要硬修：打 `needs_human`，`note` 写你看到的和它写的哪里不一样。

### 3. 要人定的，逐条

把 `ask` 和 `context` **原样**摆给用户——不缩写、不换词、不替它总结。一条摆完等拍板，再摆下一条。

拍板结果三种：
- **改**：按拍板的方案动手，改 → 测试 → 提交 → 部署，然后打 `claimed_fixed`：
  - 说法会误导（改了给模型的话）、题目有问题（改了题面或答案纸）：不带 `--data` / `--verify`。模型会不会换个走法，只能靠重跑看，你自己重放一次不算数。`decision` 是 `case` 的，改用例集也只在拍板后做。
  - 缺能力（补了工具、采集项或字段）：和确定是 bug 一样判断数据，带上 `--data`；能在原窗口复测就带 `--verify`。复测通过也不会自动关，等之后判题复验。
- **不改**：`--status wont_fix --note "<理由，用用户的原话>"`。
- **再看看**：`--status needs_human --note "<还要核什么>"`，留在清单里。

### 4. 收尾

告诉用户这几件：
- 修了几条，其中复测通过几条（已关）、复测没过几条、数据修不回来几条；
- 几条等拍板、几条不修；
- 改了哪几个仓、部署了没有。

然后讲清**建议他在页面上点哪一个按钮、为什么**。只说入口那一步：下游自动接力，点「复现」会接着诊断、判题，点「诊断」会接着判题。别说「点诊断和判题」——人会两个都点，点「判题」只是多判一次旧的诊断。页面上这道题的「复现」「诊断」「判题」按下表只亮一个（做过一次的按钮写「再次复现 / 再次诊断 / 再次判题」；「复现」在题面那一格，「诊断」「判题」在该点的那一行——原窗口那一行）：

| 修复情况 | 建议点 | 为什么 |
|---|---|---|
| 确定是 bug，数据没受影响或已修复 | 诊断 | 原窗口还能用，在上面再诊断一次（完了自动判题），看 agent 走这条路还撞不撞 |
| 确定是 bug，数据修不回来 | 复现 | 旧窗口里是错的数据，要新造现场才验得到（完了自动诊断、判题） |
| 挖出它的那次复现已过保留期 | 复现 | 旧窗口不能再诊断了 |
| 要人定·说法会误导，改了给模型的话 | 诊断 | 模型会不会换个走法只能靠重跑看 |
| 要人定·缺能力，补上了 | 同确定是 bug，按数据能不能补分两档 | 同上 |
| 要人定·题目有问题，改了答案纸 | 判题 | 诊断没变，只是判卷的标准变了，重判一次就行 |

同一道题几条问题取最上游那一个：任何一条要复现，就只建议复现，其余的跟着自动走到。你打完标记之后入口那一步已经有人点过的，不再建议；点过之后下游那条被删了的，建议断掉的那一步。

复测通过的确定是 bug 已经关了，再跑不是为了关它，是看诊断路径变了之后有没有新问题。跑出新问题就按新的处理。

**不自己触发任何重跑**：不点按钮、不调排队接口、不起 `diag-run` / `judge-run`。跑一次成本很高，跑不跑、从哪一步跑，由人定。

## 纪律

- 只改代码、配置、给模型的话、（拍板后的）用例、（能按确定规则改回来的）历史数据；**不改判题结果、不删批注、不碰复现 / 诊断 / 判题的状态**。
- 不删复现、诊断、判题。删了就是删了，会连带删掉下面的诊断、判题和 trace，不是「重来一次」。
- 一条问题一个提交；push 前必 `fetch`（五仓都有并发 agent）。
- 判题写的判定链是你信它的依据，不是替你验的：**先重放再动手**。
- 没部署、没复测，就不带 `--verify`。复测没过就写 `failed`，别不写。
- 跟用户说话按标记显示的字说：「改了，等复测」「复测通过」「复测没过」「数据修不回来，等下次诊断和判题时验证」「改了，等下次判题验证」「要人协助」「不修」。复测通过的可以说已关，其余别说「修好了」。
- 不要为了让清单变短把问题标成 `wont_fix`；理由要能让下一个人同意。

## 用户怎么说，你怎么接

- 「修这道题」「fix-run opengauss/8947f5f6」→ 第 1 步起走完。
- 「哪些等我定」→ 只导包、把 `needs-decision.md` 逐条摆出来，不动 bug 类。
- 「先修 bug 的，要人定的放着」→ 第 2 步走完就收尾，第 3 步留给下一次。
- 「X 修好了没有」→ 导包看那条的状态。确定是 bug 的、标记里复测通过、之后没有更晚跑出来的诊断又撞上，就是关了；其余看修复之后跑出来的诊断复验。还没人跑过的，告诉他建议点哪一个按钮，不自己点。
